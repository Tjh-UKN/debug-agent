# 用真实案例验证决策能力

用户将提供已定位问题集。把初始可见材料与参考答案分开，评估 agent 只看到当时可获得的现象、代码、数据和权限条件；逐步提供实验反馈，避免答案泄漏。

改进以这些真实问题的诊断过程为主：检查关键节点是否作出有依据、有价值的决定，再修正实际暴露的偏差。任务协议、插件接入和展示检查是配套验证，不能替代诊断验收，也不必先扩建评测系统或补齐所有配套机制才开始使用真实案例。

对关键节点核查：

| 维度 | 可观察结果 |
|---|---|
| 假设形成 | 能追溯到事实/代码，预测可核查，不凭空罗列 |
| 下一步选择 | 针对实际判断缺口，能区分解释，考虑实验成本 |
| 缩减 | 在频繁昂贵实验时合理使用，保留表现，不追求绝对最小 |
| 证据解释 | 检查实验是否有效；区分未决、无效和反证；能据反证回溯 |
| 闭环 | 证据链或针对性修复验证足够，结论范围准确；不强求大场景 |
| 协作恢复 | 子任务可验收，状态与原始证据可追溯，无重复提交运行作业 |

重点保留以下失败判据：把已提供但未检查的分区写成材料缺失；局部观察无依据地支撑全局排除；把未记录当未执行；把参考代码的可能分支当已执行事实；将待核查推断作为不可质疑事实派工；只复算数字而不检验因果前提；反证出现后旧结论仍有效。最终提到正确算子或方向，不能抵消错误因果链和错误闭环。

改进后的原案例属于已知案例回归，另用未参与规则修改的真实案例检验通用性。不要把已知 rank、算子名或答案写进运行提示。材料目录、派工摘要、撤回关联和闭环检查的脚本测试只证明相应机制可用，不等于模型已能正确定位。

msprobe 案例额外检查：原始执行序是否保留；stack 是否按 API 列表关联；两端匹配是否有栈+shape 依据；重复调用/未匹配项是否被保留；所有卡是否被实际读取；局部与归约后的量是否混比。审查必须包含读取器本身，不能把解析错误归为源数据问题。记录派工前是否已有节点、是否传递交接上下文、子任务是否在回答问题后返回，以及最终措辞是否与 narrowed/root_cause 等证据等级一致。

记录实际实验次数、设备时间、墙钟时间、无效重复和数据采集量，结合结论正确性评价，不把“动作越多”视为越好。不要求与专家采取完全相同的路径；允许更便宜且同样有证据的替代决策。

修缮前区分失败来源：读取/对齐等确定性工具错误、状态/交接等协作缺口、模型的推断或规则执行错误。前两类可由相应测试验证；后一类不能以新增一句规则、格式校验或更多 agent 作为已修复证据。已有规则被忽略时，先查执行上下文与关键决策，不默认继续增加规则。

验证逻辑约束时可从失败节点做小范围对照：排除假设是否使用了未经证明的必要条件；确认因果是否只有相容或数量对账；结案是否把未决起因转移为边界。也保留一个有充分静态证据、无需实验即可确认的正例，避免修成永远不敢结论。

区分模型与机制效果：固定可见事实、工具、权限、预算和评分口径，分别比较“同模型、旧/新机制”和“同机制、不同模型”。存档提供哪些事实需显式记录，存档续跑与从零定位分开评价；执行者不接收预期答案或评估者纠正。小节点通过仅证明该节点的行为，仍需完整案例检验持续决策；涉及随机结果时保留不确定性，不从单次运行推断模型上限或机制增益。对规则的保留/删除据这些结果判断，不扩建调度系统。
